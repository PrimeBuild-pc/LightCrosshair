# Microsoft Store (MSIX)

How to build the Store package and submit LightCrosshair in Partner Center. The ZIP and Inno Setup builds are unchanged; this is a third channel built from the same code.

## What the package contains

- One MSIX per architecture (x64, ARM64), combined into `LightCrosshair_<version>.0.msixbundle`.
- Both executables in one folder: `LightCrosshair.exe` (entry point: tray, overlay, hotkeys) starts `LightCrosshair.UI.exe` from the same folder, as in the ZIP.
- The .NET 10 runtime, self-contained. The Store cannot install the .NET Desktop Runtime for a desktop (full trust) app, and there is no .NET 10 framework package for MSIX, so the runtime has to ship inside the package. Core and UI share one copy of it.
- Logos generated by `scripts/assets/make-msix-assets.py` from the same `draw()` that produces `LightCrosshair/assets/icon.ico`, so every size is pixel-exact.
- Manifest: [`packaging/msix/Package.appxmanifest`](../packaging/msix/Package.appxmanifest). Capability `runFullTrust` only. Minimum Windows 10 2004 (build 19041).

Size, measured for 2.0.0:

| Build | Download | On disk |
|---|---|---|
| ZIP x64 (framework-dependent, needs .NET 10 Desktop Runtime) | 6.1 MB | 15.4 MB |
| MSIX x64 (self-contained) | 75 MB | 181 MB |
| MSIX ARM64 (self-contained) | 71 MB | 200 MB |

The Store delivers only the package for the user's architecture from the bundle. Trimming is not supported for WinForms/WPF, so the runtime cannot be made smaller safely.

## What behaves differently when packaged

The binaries are identical; the app checks its package identity at run time (`GetCurrentPackageFullName`).

| Area | ZIP / installer | Store package |
|---|---|---|
| Start with Windows | `HKCU\...\Run` value | `windows.startupTask` in the manifest (`LightCrosshairStartup`, off by default). The Settings switch shows the real Windows state: if the user turns LightCrosshair off in Task Manager > Startup apps, the switch shows off, and the app cannot turn it back on (Windows rule); a line under the switch says where to turn it on. |
| Updates | Settings > Updates checks GitHub on request | The Updates section is hidden; the Store updates the app. The packaged app makes no network requests. |
| Data | `%AppData%\LightCrosshair\v2` | See below. |

### Data location and 1.9 migration

MSIX redirects *new* folders created directly under `%AppData%` to a private per-package folder, and lets the app edit files and folders that already exist. Measured in Windows Sandbox (Windows 11 26100) with the test package:

| Situation | Where v2 data lives | Result |
|---|---|---|
| Fresh user (no `%AppData%\LightCrosshair`) | `%LocalAppData%\Packages\<package family>\LocalCache\Roaming\LightCrosshair\v2` (private) | Works. Removed when the app is uninstalled. |
| 1.9 user (`%AppData%\LightCrosshair` exists) | `%AppData%\LightCrosshair\v2` (real folder, because the parent already exists) | Migration from 1.9 works, v1 files untouched (hashes compared). Kept after uninstall, like the installer build. |
| Existing ZIP/installer 2.0 user | `%AppData%\LightCrosshair\v2` (real) | The Store app reads and saves the same `store.json`; settings survive restart. |

Also verified in both cases: settings persist across restart, a corrupt `store.json` is set aside as `store.corrupt-*.json` and the latest backup is loaded, the core log is written. No manifest change is needed (excluding the folder from virtualization would require the extra restricted capability `unvirtualizedResources`).

### Other packaged-app checks

| Check | Result |
|---|---|
| Runs without .NET installed | Yes (Sandbox has no .NET). Tested with the x64 package; the ARM64 package is built the same way but was not run (no ARM64 machine). |
| Start with Windows | Switch on → task state Enabled; off → Disabled; Task Manager's "disabled by user" shows as off and the app cannot override it; no Run key is written. Starting at the next sign-in was not tested (Sandbox cannot sign out). |
| Overlay, tray, FPS overlay, settings UI | Run from the package. The UI started by Core inherits the package identity. |
| Named pipe Core ⇄ UI | Same name and behavior (full trust is not an AppContainer). |
| Low-level keyboard hook, raw input | No restriction for full trust apps; same code path. |
| NVIDIA helper | Core starts itself with helper arguments from the package folder and uses `%TEMP%`, both allowed. Not tested on NVIDIA hardware in the Sandbox (no NVIDIA driver there). |
| FPS overlay (ETW) | Same as the ZIP: the ETW session started both packaged and unpackaged under the same user. ETW real-time sessions need an administrator token or membership in the *Performance Log Users* group; packaging changes neither. A standard user who sees "FPS capture needs permission" must be added to Performance Log Users (`lusrmgr.msc` or `net localgroup "Performance Log Users" <user> /add`, then sign out and in). The Store package does not request elevation. |
| Installed next to the Inno/ZIP version | Both can be installed. Both cores use the same single-instance mutex, so only the first one started runs; the second exits. Both can register start with Windows (Run key and startup task); whichever starts first wins. Recommend uninstalling the other version. |
| Uninstall while running | Windows closes both processes; nothing keeps running. |

## Build

Needs the .NET SDK used by the solution and the Windows SDK tools `makeappx.exe`, `makepri.exe`, `signtool.exe` (Visual Studio Installer > Individual components > Windows 11 SDK, or `winget install Microsoft.WindowsSDK.10.0.26100`).

```powershell
./scripts/build-msix.ps1 -Version 2.0.0
```

Output in `releases/msix/`: `LightCrosshair_2.0.0.0.msixbundle` (upload this), the per-architecture `.msix` files in `bundle-input/`, and the unpacked layouts. Do not sign the Store upload: Microsoft signs it after certification.

### Local sideload test

```powershell
./scripts/build-msix.ps1 -Version 2.0.0 -Sign
```

`-Sign` creates (once) a self-signed certificate in *CurrentUser\My* whose subject equals the manifest `Publisher`, signs the bundle and exports `LightCrosshair-test.cer`. On the test machine (a VM or Windows Sandbox, not your daily system): import the `.cer` into *Local Machine > Trusted People*, then open the bundle or run `Add-AppxPackage`. Rebuild with the same identity you will upload; a sideloaded test package and the Store package with the same identity replace each other.

### Windows App Certification Kit

Partner Center runs the same checks on upload, but running WACK first saves a round trip. WACK installs and launches the package, so run it in the test VM or another clean machine, not on a PC with your own LightCrosshair data (it would migrate and edit `%AppData%\LightCrosshair`). Test the signed x64 package, not the bundle (WACK 10.0.26100 cannot pick a package from a bundle):

```powershell
# in the test machine, elevated, after importing LightCrosshair-test.cer into Local Machine > Trusted People
& "${env:ProgramFiles(x86)}\Windows Kits\10\App Certification Kit\appcert.exe" reset
& "${env:ProgramFiles(x86)}\Windows Kits\10\App Certification Kit\appcert.exe" test -appxpackagepath C:\path\LightCrosshair_2.0.0.0_x64.msix -reportoutputpath C:\path\wack.xml
```

Sign the per-architecture package for this with `signtool sign /fd SHA256 /sha1 <thumbprint of "LightCrosshair MSIX test"> /s My <msix>`.

Status for 2.0.0: not yet run. The Hyper-V test VM rejected the stored credentials, and in Windows Sandbox the kit's own installer failed (MSI error 1603), so every test ended with a TAEF start-up error instead of a result.

## Partner Center submission

Product: **LightCrosshair**, Store ID `9MZ2872MWBJL` (<https://apps.microsoft.com/detail/9MZ2872MWBJL>). The manifest already carries its identity: `LorenzoMassafra.LightCrosshair`, publisher `CN=ACD03D0F-7A52-4C93-ADF8-A07702180E72`, display name `Prime Build`.

1. **Account.** Sign in at <https://partner.microsoft.com/dashboard> with the developer account (individual is enough).
2. **Reserve the name.** Apps and games > New product > MSIX or PWA app > name `LightCrosshair`.
3. **Fill the identity.** Product management > Product identity. Copy the three values into the marked block at the top of `packaging/msix/Package.appxmanifest`:
   - `Package/Identity/Name` → `Identity Name`
   - `Package/Identity/Publisher` → `Identity Publisher` (starts with `CN=`)
   - `Package/Properties/PublisherDisplayName` → `PublisherDisplayName`

   This is the only place to edit. The build script warns while the placeholders are still there.
4. **Build** with `./scripts/build-msix.ps1 -Version 2.0.0` (no `-Sign`). The version must increase for every upload; the fourth number stays 0.
5. **Start a submission.**
   - *Pricing and availability*: Free, all markets (or your choice). Visibility public.
   - *Properties*: Category **Utilities & tools** (subcategory none). System requirements: keyboard and mouse recommended. Do not tick "requires a game controller". Product declarations: none apply.
   - *Age ratings*: answer the IARC questionnaire (below).
   - *Packages*: upload `LightCrosshair_2.0.0.0.msixbundle`. Device families: Windows 10/11 Desktop only.
   - *Store listings*: add English (United States) and Italian; paste the texts below. Screenshots: at least one 1366×768 or larger PNG per language; `docs/images/ui-*.png` can be used.
   - *Submission options > Notes for certification*: paste the restricted-capability justification and the testing note below.
6. **Submit.** Certification usually takes 1–3 working days. If it fails, the report names the policy; fix, increase the version and resubmit.

Updates later: increase `-Version`, rebuild, create a new submission and replace the package.

### Restricted capability justification (`runFullTrust`)

> LightCrosshair is a classic Win32 desktop application (WinForms and WPF on .NET 10) packaged with MSIX. It needs runFullTrust because it runs as a standard desktop process: it shows a click-through, always-on-top layered window that draws a crosshair at the screen center, a notification-area icon, global hotkeys (RegisterHotKey and a low-level keyboard hook, used only to detect the user's configured hotkeys; keystrokes are passed on and never stored or sent), raw mouse input for "hold to hide" bindings, foreground-window detection to switch per-game profiles, optional display gamma/vibrance through the Windows GDI gamma ramp and the AMD/NVIDIA display driver APIs, and an optional FPS counter based on Windows ETW present events. The settings window is a second executable in the same package that talks to the main process through a named pipe restricted to the current user. The app does not inject code into other processes, does not read or write game memory, does not capture the screen, installs no drivers or services, and makes no network requests.

### Notes for certification (testing)

> After launch, LightCrosshair runs in the notification area (tray) and shows a red crosshair at the center of the primary screen. Double-click the tray icon or press Alt+L to open Settings. Alt+X shows/hides the crosshair. The FPS overlay (FPS overlay page) needs an administrator account or membership in the Performance Log Users group; otherwise it shows "FPS capture needs permission", which is expected. No account or sign-in is required.

### Age rating (IARC questionnaire)

The app has no violence, sexual content, gambling, purchases, chat, user-generated content sharing with other users, or location sharing. Answer **No** to every content and interaction question; category "Utility / productivity app" if asked. Expected result: the lowest rating in every region (for example IARC 3+, PEGI 3, ESRB Everyone). A crosshair is a UI element, not depicted violence.

### Privacy policy

The Store build collects no personal data and makes no network requests (the optional GitHub update check exists only in the ZIP/installer build). Partner Center asks for a privacy policy URL only when the product accesses or transmits personal information, so it is not strictly required; providing one avoids questions during certification. A short page on primebuild.website is enough, for example:

> LightCrosshair does not collect, store or transmit personal data. All settings, crosshairs and game profiles are saved locally on your PC in your user folder. The Microsoft Store version makes no network connections. Uninstalling the app removes its data, except data in %AppData%\LightCrosshair created by an earlier non-Store version.
